# 连载叙事义务账本

连续项目中，伏笔、未支付代价、待回答的问题和已启动的决定都是叙事义务。它们不是“神秘元素库存”，而是限制下一集选择并在未来必须以结果回应的承诺。本文件只在连续项目、续写或有跨集谜题时使用；单元剧或没有活跃义务时不要求人为建立账本。

## 1. 账本与单集地图的分工

`story-engine.md` 的“铺垫与兑现义务”表保存每条义务的稳定 ID、当前问题、计划兑现条件和总状态。`episode-map.jsonl#hook_operations` 只记录本集的状态变化：

| operation | 可以做什么 | 必须记录 |
|---|---|---|
| `seed` | 建立一条新义务 | 当前观众问题、可见载体、它立刻改变的行动、计划兑现条件 |
| `advance` | 给既有义务增加可用压力或证据 | 本集载体，以及人物现在必须怎样改选/付代价 |
| `resolve` | 回答承诺的问题并留下结果 | 兑现载体、答案如何改变当前选择、已落地的后果 |
| `defer` | 有意延后，但不假装推进 | 延后的原因、保留的压力、下一次何时/在什么条件下重审 |

不要为“角色又提了一遍”“出现同类物件”“结尾留了神秘一句”写 `advance`。这些可以是气氛、回声或提示；只有它改变人物的行动权限、代价、选择或观众对即将到来的后果的判断，才是推进。

## 2. 写前选择义务

写每集前，先从活跃账本中选择本集要承担的义务，并分别回答：

```text
本集正在处理的义务：H___
此刻观众在等什么回答或后果：
本集给出的局部回报：
可见载体：
载体最多直接证明什么：
仍然不能断言什么：
谁因此必须改选、失去退路或付出代价：
```

一集可以没有 `advance`，但不能把没有贡献的复述包装成推进。若不处理某条活跃义务，先确认它为何能暂时留在后台：本集是否在结算更近的后果、切换焦点人物，或让旧义务因已知状态仍保持压力。新建义务前问：现有义务是否已足够产生下一步冲突？若足够，优先推进或兑现现有义务，避免无止境加谜。

## 3. 兑现不是解释

`resolve` 不等于角色给出一句答案。兑现至少完成两件事：

1. 回答或改义此前承诺的问题，且观众能追溯到原始载体；
2. 让答案进入当前冲突，改变某人的选择、关系、权力、风险或已付代价。

例如“账本属于谁”被回答后，持有人必须决定公开、交换、销毁或承担责任；若答案没有产生任何当下后果，它更像设定补充而不是戏剧兑现。

允许“部分兑现”：明确写本次回答了哪个子问题，哪个问题仍保持 `open` 或 `progressing`。不要把未完成的谜题误标 `resolved`，也不要在已经 `resolved` 后用同一 ID 再次开启同一个谜。

## 4. 状态与审查

状态只表示叙事义务，而不是情绪热度：

- `open`：已建立、尚未获得新的行动性证据；
- `progressing`：本集的载体使选择或后果发生了可引用的变化；
- `deferred`：创作者有意延后，并写清保留压力与重审条件；
- `resolved`：承诺问题获得结果，结果已进入当前故事状态。

发布前运行：

```bash
python3 <skill-dir>/scripts/episode_map_check.py 项目开发/episode-map.jsonl \
  --story-engine 项目开发/story-engine.md
```

带 `--story-engine` 时，校验器还要求每个操作的稳定 ID 存在于权威账本、账本有计划兑现条件、地图终态与账本状态一致。导入只包含中后段的历史地图时，显式加 `--allow-inherited-ledger`，让首次本地操作以账本中既有义务为来源；不要把它用于掩盖漏掉的 seed。它不评价谜题是否有趣、答案是否够强或节奏是否合适；这些由 `$short-drama-review` 依据文本证据审查。

## 5. 修订顺序

发现连载失速时按以下顺序修订：

1. 标出每条活跃义务最近一次真正改变了什么，而不是最近一次被提到的位置；
2. 删除或降级只重复问题的“推进”；
3. 给至少一条活跃义务补上能改变人物选择的可见后果，或明确其延期理由；
4. 若需要新义务，先说明旧义务为什么不足以承载新的压力；
5. 将本集兑现带来的知识、持物、关系和决定写进 `handoff_state`，让下一集不重置结果。

这不是要求每集都反转、兑现或新埋伏笔。它只要求声称发生了叙事推进时，能说明什么被推进，以及它让谁必须做出不同的下一步。
